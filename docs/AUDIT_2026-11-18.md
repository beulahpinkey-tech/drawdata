# DrawData audit: 2026-11-18

**Target:** https://draw-data.com (production) · **Scope:** the whole public site; no user accounts exist, so there was no authenticated scope · **Prior audit:** [AUDIT_2026-11.md](AUDIT_2026-11.md) (2026-11-17)

**Method.** This run re-verified the previous audit's claims independently rather than restating them, and covered three things it did not: the Cloudflare CPU failures seen in October, accessibility, and whether the recommended monitoring was ever configured. Every number below came from a command whose output is quoted in the evidence appendix. Requests to production were serialised at roughly one per second, with one deliberate 12-request burst at concurrency 3 (§3.1). No load testing, no exploitation, no form submissions, no third-party probing.

---

## 1. Executive summary

The site is **healthy and materially better than six weeks ago**. The October Cloudflare `1102 Worker exceeded resource limits` failures did not reproduce: 75 URLs sampled across all 28 route templates returned 200, and a small concurrency burst stayed clean. All 27 datasets are current. The regression suite reproduces yesterday's result exactly — **142 passed, 8 failed, 2 skipped** — and all 8 failures are the single HSTS item that only the account owner can fix.

**One new user-visible defect was found and fixed in this run (F-08):** the homepage card for New York reads **"York Numbers · Win 4"**. The heading is built by taking the last two words of the game label, which works for every state except the one whose name is two words. It is on the homepage, so every visitor sees it.

**Open and unchanged:** HSTS is disabled at Cloudflare (S-01, owner action, 2 minutes). Layout shift is still poor on client-rendered panels (P-02, re-measured below). Four dependency advisories now, up from one (S-02). `www.draw-data.com` still has no DNS record (S-06).

**Correcting an earlier recommendation of mine:** the previous audit's top monitoring item — run the e2e suite against production on a schedule — cannot work as written. Cloudflare bot protection serves GitHub Actions' datacenter IPs a challenge page instead of the site (documented in `.github/workflows/freshness-check.yml`). §7 proposes a version that does work.

## 3. Findings

### 3.1 The October CPU failures did not reproduce — RESOLVED

In October, dynamic routes intermittently returned `503` with Cloudflare `error code: 1102`, including under single-request-per-5-seconds pacing. That is the failure most likely to have produced Search Console's persistent "Server error (5xx)" bucket.

| Probe | Result |
|---|---|
| 75 URLs, ≥1 per template, ~1 req/s | **75/75 → 200** |
| TTFB across that sample | p50 **0.99 s**, p90 **1.51 s**, max 3.18 s |
| 12 URLs at concurrency 3, then 2 serial follow-ups | **14/14 → 200**, no degradation |

Not re-tested: heavy sustained concurrency. I caused a real outage with that in October and did not repeat it. So this is "did not reproduce under realistic pacing", not "proven immune under crawl load".

### 3.2 New finding

| ID | Severity | Finding | Status |
|---|---|---|---|
| **F-08** | Medium (visible on every homepage visit) | The homepage card heading for New York reads **"York Numbers · Win 4"**. `GroupPanel` built the heading with `label.split(" ").slice(-2).join(" ")` — the last two words of "New York Numbers" are "York Numbers". New York is the only state with a two-word name, so the heuristic is correct on all 13 others, which is why it survived. | **Fixed in this run.** The server now passes `GAME_SHORT` (`ny-pick3` → `Numbers`) and the client stops re-deriving copy, which is what the component's own documentation says it should do. Regression test added. |

The test deserves a note, because its first version was **worse than useless**: it asserted `headings.join(" | ")).toContain("Numbers · Win 4")`, and `"York Numbers · Win 4"` contains that substring, so it passed against the broken page. It now compares array elements exactly, and it fails against production (screenshot and trace in `test-results/`) and passes against the fix.

### 3.4 Accessibility (new coverage, structural only)

Six pages probed. `lang="en"`, exactly one `h1`, and `main`/`nav`/`header`/`footer` landmarks on all six; zero images without `alt`; zero buttons or links without an accessible name; zero unlabelled inputs except one false positive.

| ID | Severity | Finding |
|---|---|---|
| A-01 | Low | The homepage heading outline skips a level: `h1` → `h3` for the game cards, with the `h2` sections appearing after them. Screen-reader users navigating by heading get a confusing outline. |
| A-02 | Low | `/contact` has an unlabelled text input named `website`. It is an intentional spam honeypot positioned off-screen — **not a defect** — but it is still focusable and announced. Adding `aria-hidden="true"`, `tabindex="-1"` and `autocomplete="off"` would hide it from assistive tech without weakening it. |

Not covered: colour contrast, focus visibility and order, screen-reader semantics of the canvas visualisations (`/combinations` renders 10,000 points on a canvas; it has a documented text fallback, which was not verified with a screen reader), reduced-motion behaviour, and keyboard traps in the modals.

## 8. Monitoring — correcting the previous recommendation

The prior audit's item 1 was "run `npm run test:e2e` against production daily from GitHub Actions". **That cannot work.** Cloudflare bot protection serves Actions' datacenter IPs a challenge instead of the page; the repo already documents this as the reason `freshness-check.yml` queries the Cloudflare API instead of scraping.

What works instead:

1. **Run the suite in CI against a production build of the app** (`next build && next start`, `BASE_URL=http://localhost:3000`). This catches the F-01 and F-08 classes — data plumbing and rendered copy — which are the regressions that actually shipped. It cannot check Cloudflare-level configuration (HSTS, edge headers), so keep those assertions in a manual or self-hosted run.
2. **Keep `freshness-check.yml`** for deployment health, and add the three `CF_*` secrets so it stops passing with a note.
3. **Data staleness is already gated** in `pa-refresh.yml` — it fails when any game goes stale. That recommendation is done.
4. **TLS expiry:** certificate renews automatically, but an external expiry alert at 14 days is still worth having; nothing watches it today.
5. **Field performance:** watch CLS in Search Console after item 4 — lab numbers alone will not tell you whether real users see the shift.
